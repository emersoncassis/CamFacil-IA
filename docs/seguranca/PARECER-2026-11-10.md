## Achados

### 1. Segredos no código e no histórico (Alta)

`crates/cf-notify/src/telegram.rs` tinha um token de bot do Telegram num teste, e `scripts/telas-mcp-https.py` tinha um token de acesso do MCP. Como o repositório é público, ambos foram tratados como vazados.

Feito:
- Teste do Telegram usa token sintético montado na hora; o script lê `CFIA_TEST_MCP_TOKEN` e falha com mensagem clara se faltar. `.env.example` criado; `.env` segue no `.gitignore`.
- Histórico reescrito com `git filter-repo` em todos os 142 commits, branches e as 29 tags; nenhuma ocorrência dos valores restou.
- Os dois tokens foram revogados pelo dono do projeto.
- Ticket #4980723 aberto no suporte do GitHub para apagar o cache dos commits antigos e o ref `refs/pull/1/head` do PR #1.

Pendente fora do nosso alcance: os forks `FelipeDuarteFerreira/CamFacil-IA` e `digofd/CamFacil-IA` foram criados antes da limpeza e guardam o histórico antigo. Como os tokens foram revogados, o que ficou lá não serve mais.

### 2. CSRF na dashboard local (Alta)

A dashboard local não tem login quando roda só na máquina (`127.0.0.1`), e não conferia de onde vinham os pedidos. Rotas com corpo JSON já estavam protegidas pelo próprio navegador (o pedido exige pré-checagem CORS), mas as demais não:

- `POST /api/backup/importar` aceita o corpo cru. Um site qualquer podia mandar um backup montado pelo atacante, com a senha dele, e trocar a configuração (por exemplo, os contatos do Telegram que recebem as fotos das câmeras).
- Rotas `POST` sem corpo (`/api/elo/desparear`, `/api/mcp/token`, `/api/ia/baixar`, `/api/whatsapp/qr`, testes de envio etc.) podiam ser disparadas por qualquer página.

Correção: `crates/camfacil/src/protecao.rs`, aplicado a todas as rotas. Se o navegador manda `Origin`, ele precisa ser o próprio endereço da dashboard; `Origin: null` é recusado; navegador antigo sem `Origin` tem os pedidos que mudam algo recusados quando `Sec-Fetch-Site: cross-site`. Clientes que não são navegador (MCP, curl, Evolution API) não mandam `Origin` e seguem funcionando.

### 3. DNS rebinding na dashboard local (Alta)

Um site pode fazer o próprio domínio apontar para `127.0.0.1` e o navegador passa a tratá-lo como "mesma origem" da dashboard, com leitura e escrita completas da API (câmeras, configuração do MCP, acionar rotas). A rota `/mcp` já se protegia; o resto da API não.

Correção (mesmo módulo): o cabeçalho `Host` só é aceito se for `localhost`, um IP, um nome de rede local (sem ponto ou `.local`), o Tailscale (`*.ts.net`) ou o túnel do ngrok. Qualquer outro nome recebe 403.

Teste com o programa rodando: `Host: atacante.com` → 403; `Origin` de outro site importando backup → 403; `Sec-Fetch-Site: cross-site` → 403; `Origin: null` → 403. Dashboard, `curl` sem `Origin` e `Host` do Tailscale seguem passando.

### 4. Workflows sem `permissions` (Média)

`rust.yml` e `docs.yml` rodavam com as permissões padrão do `GITHUB_TOKEN`. Agora declaram `permissions: contents: read` no topo; os jobs que publicam (`release`, `imagem-api`) já pedem o que precisam no próprio bloco.

### 5. Dependências com alerta RustSec (Baixa, aceito)

- `rsa` 0.9.10 — RUSTSEC-2023-0071 (Marvin Attack).
- `crypto-bigint` 0.5.5 — RUSTSEC-2026-0387 (tempo variável).

Ambos chegam só pelo `jsonwebtoken` da `cfia-api`, que verifica o ID token do Google com `Algorithm::RS256` e chave pública. Os ataques exigem operações com chave privada, que o projeto não faz. Não há versão corrigida compatível com o `jsonwebtoken` 11. Registrados em `.cargo/audit.toml` com a justificativa; rever ao atualizar o `jsonwebtoken`.

### 6. Modo `--lan` sem login (Média, recomendação)

Com `--lan`, qualquer aparelho na rede da loja abre a dashboard completa. Ações físicas (portão/relé) já exigem PIN, confirmação e log, e o MCP nunca aciona portão (regra 7 do `CLAUDE.md`), mas configuração, câmeras e integrações ficam abertas. O app Android também fala HTTP puro na rede local (`cleartextTrafficPermitted`), o que é esperado para IP da loja e coberto pelo Tailscale para acesso de fora.

Recomendação: senha ou PIN de acesso à dashboard quando ela escuta fora de `127.0.0.1`. É mudança de comportamento visível, então pede ADR (0017) e atualização do SDD-05.

## O que já estava bem feito

- Segredos do programa guardados cifrados no cofre (ChaCha20-Poly1305); backup exportado cifrado com senha.
- MCP desligado por padrão, token comparado em tempo constante, token na URL aceito só via proxy HTTPS local.
- Túnel do ngrok para a dashboard com usuário e senha por arquivo de política (a senha não aparece no `ps`).
- API da nuvem: login Google com PKCE, `state` e `nonce`; cookie `HttpOnly; Secure; SameSite=Lax`; checagem de `Origin` em tudo que muda algo; WebSocket do painel confere origem; Row-Level Security no Postgres com `SET LOCAL ROLE cfia_app` em toda transação; redirecionamento pós-login só para caminho local; downloads só de uma lista fixa.
- Caminhos de arquivo validados (relatórios, receitas do estúdio); download do ngrok extrai só o binário esperado.
- Deploy: imagem distroless `nonroot`, Postgres sem porta publicada, senhas só por variável de ambiente.
- Android: `allowBackup=false`, componentes não exportados exceto o lançador e o receptor de boot; a ponte JavaScript atende só a página interna do app.
